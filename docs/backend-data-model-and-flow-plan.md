# ProTangram 后端数据模型与流转规划

本文仅明确业务数据、关系、流转及验收要求，不指定数据库、表结构、技术框架或代码组织方式；具体实现由后端开发者自行设计。

## 当前情况

后端主要集中在 backend/src/index.js，试验卡片、模板、项目、报告和计算记录主要以 JSON 文件保存。前端核心业务数据由 Zustand/localStorage 保存，原始 CSV 文件放在 IndexedDB；现有 API 层主要覆盖旧的试验卡片、模板、项目和报告接口。因此，物理对象、具体试验、执行记录、文件、图表成果和模型尚未形成统一的后端持久化及关系管理能力。

## 需要统一管理的数据

- 对象与设计：对象类别、具体物理对象、参数、组成和对象关系；区分设计方案/设计值与实际对象状态，并保留技术状态变更的追溯关系。
- 试验过程：试验定义、具体试验、执行记录；记录实际条件、测量信息、时间及关联对象。一次试验可以涉及多个对象，必需与可选关联应按业务含义确定。
- 文件与数据：原始文件、文件元信息、采集格式 FMT、列名/物理量/单位映射、解析数据及派生数据。原始文件保留不变，派生数据记录来源；不同文件暂不自动做时间对齐。
- 图表与分析成果：图表配置、数据表、分析结果及其来源记录、文件和上游成果。成果应能追溯到执行记录与源文件。
- 模型与运行：MODEL 为通用模型，OM 为应用到具体对象的对象模型；记录模型版本、适用对象、参数来源、可选标定记录，以及每次运行的输入、输出和来源。
- 项目与任务书：负责组织、关联和汇总，不复制具体试验、执行记录、文件或成果。具体试验可以独立存在、后续再关联任务书，也可以被多个项目引用。

## HTML 与前端概念的映射

HTML 使用 TASK、SUBJ、SET、REC 表示试验任务、试验科目、试验设置和实际执行记录；CFG 是由被试对象、供电对象和陪试件组成的试验构型，PROG 是程序/载荷谱，COND 是工况，REQ 是要求集，FMT 是采集格式，DOC 是文档。

前端使用“对象类别 → 具体物理对象 → ExperimentDefinition → ConcreteTrial → TestRecord”。请后端给出简明映射表，说明哪些概念可直接对应、哪些需要转换。特别需要区分 HTML 的 CFG 与前端的具体物理对象，并明确设计方案与实物实例、试验设置与实际执行记录的边界；不能只凭名称强行一一对应。

## 推进顺序

1. 先明确概念映射、核心数据字段/类型、必需与可选关联规则和数据流图，只列影响数据正确性或后续扩展的未决问题。
2. 建立对象、试验、执行记录及关系的持久化和查询能力，不要求一次实现 HTML 中的全部类和专业字段。
3. 打通原始文件导入、解析数据、图表与分析成果的来源追溯。
4. 建立模型版本、对象模型、运行输入输出及来源数据的注册和留痕。
5. 再将前端浏览器本地数据接入后端，保留原 ID、关系和历史成果；迁移前明确备份、核对和失败恢复。

## 最低验收要求

- 不依赖项目或任务书即可创建具体试验，后续可以补充或调整关联。
- 同一具体试验可被多个项目引用，项目/任务书汇总读取同一份数据，不产生副本。
- 一次执行记录可关联多个实际对象，并明确哪些关联必需、哪些可选。
- 原始文件、解析数据、图表和分析成果可以互相追溯，分析流程不覆盖原始文件。
- 模型版本、对象模型、运行输入输出和来源数据可以关联查询。
- 迁移前后保留试验、执行记录、文件、图表及项目/任务书关联，并能核对迁移结果。

交付以简明关系图、字段/类型表、概念映射表和分阶段验收结果为主。数据库选型、表如何拆分、接口如何组织及代码如何重构由后端开发者自行决定；不为追求抽象完整性一次性建设复杂平台。
